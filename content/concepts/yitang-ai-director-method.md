# 王欢·AI 导演方法论

> 一堂专家分享（王欢）：从"AI 演员到 AI 导演"的身份切换出发，给出 BTICOE 提示词框架、上下文工程三层、AI 业务档案、生成/验收分离、飞轮设计等完整方法论。核心主张：**AI 时代最稀缺的不是工具，而是你对业务、用户、场景、标准的判断力**。

**回放**：https://air.yitang.top/live/UdFHDT40Yt
**讲师**：王欢（huanwang.org）

## 核心区分：演员 vs 导演

| | 演员 | 导演 |
|---|---|---|
| 模式 | 我做事，AI 帮我 | 我定义事，AI 执行，我验收 |
| 提升 | 20-50%（线性） | 3-10 倍（系统级跃升） |
| AI 角色 | 道具 | 执行团队 |
| 人的核心能力 | 亲自执行 | 定义 + 验收 |

> 导演的工作 = 定义（开头）+ 验收（结尾）。中间的执行交给 AI。

## 五层 AI 能力模型

| 层级 | 描述 | 目标 |
|---|---|---|
| 第五层 · 系统层 | AI 业务系统自动运转 | |
| 第四层 · 产品层 | 真实用户在用的 AI 产品 | |
| **第三层 · 作品层** | **可验证的真实产出** | ← **今天目标线** |
| **第二层 · 工作流层** | **AI 稳定嵌进每周工作** | ← **今天打基础** |
| 第一层 · 问答层 | 理解 AI 能力边界 | ← 今天完成 |

> [!warning] 第二层是地基
> 很多人跳着往上冲，想直接做第四层、第五层，但第二层没扎实。地基不稳，上面盖得越高越危险。

## BTICOE 提示词框架

| 要素 | 全称 | 作用 | 消灭的模糊 |
|---|---|---|---|
| **B** | Background | 背景 | AI 不知道你是谁、什么处境 |
| **T** | Task | 任务 | AI 不知道你要解决什么 |
| **I** | Instruction | 指令 | AI 不知道按什么思路做 |
| **C** | Constraint | 约束 | AI 不知道边界和禁忌 |
| **O** | Output | 输出 | AI 不知道要什么格式 |
| **E** | Example | 示例 | AI 不知道什么算"好" |

> [!summary] BTICOE 的本质
> BTICOE 不是公式，是一种习惯：在开口之前，把所有的模糊系统性地消灭干净。**最大的价值不是让 AI 更好——是逼你自己想更清楚。**

### 三版对比（企业培训顾问丢客户场景）

| 版本 | 输入 | 输出质量 |
|---|---|---|
| 零上下文 | "我丢了一个大客户，帮我分析原因" | 五条通用排列组合，不能用于决策 |
| 有一点上下文 | 加了行业和基本背景 | 有针对性了，但还是在猜 |
| **BTICOE 完整版** | B+T+I+C+O+E 全部写清 | AI 识别到"老板没出席结项汇报"这个关键信号，给出三个可验证动作，**明天可以直接拿来做决策** |

## 上下文工程（三层）

> 来源：Anthropic 工程博客

| 层次 | 名称 | 说明 |
|---|---|---|
| Level 1 | 会话级 = BTICOE | 每次对话把背景说清楚 |
| Level 2 | 项目级 = 知识库注入 | 把行业知识/SOP 整理成文档注入 |
| Level 3 | 系统级 = System Prompt | 给 AI 建"人格设定"，自动载入业务上下文 |

- **提示词工程**：这一次怎么问出好结果？单次优化，换对话从零开始
- **上下文工程**：如何让 AI 长期"住在"我的业务里？跨对话积累，越用越懂你

## AI 业务档案（Level 2 落地）

五个字段：

| 字段 | 写法要点 | 反例 → 正例 |
|---|---|---|
| **关于我** | 角色和核心职责 | "某公司中层" → "我每周审15份采购合同" |
| **我服务谁** | 客户/上级/协作方在乎什么、怕什么 | |
| **我的风格偏好** | 表达习惯 | "不用感叹号""先结论后原因" |
| **行业暗规则** | 不说但默认的事 | "报价永远留8%谈判空间" |
| **我的输出标准** | 不是格式，是底线 | "不许出现未经验证的第三方数据" |

> [!note] 使用方式
> 每次跟 AI 开新对话，第一步粘档案。用一周后你会主动往里加东西。它在长大。

## 驾驭工程：生成 / 验收分离

```
生成者：让 AI 去做 → 目标：产出
验收者：看结果找毛病 → 目标：找问题
```

> [!warning] 两个角色合在一个人身上 = 盲区
> 生成者的目标是产出，验收者的目标是找毛病，这两个目标有内在冲突。自己写的文章自己审，觉得没问题，发出去别人一眼看到三处错误。

**实验对比**（AI 做游戏）：
- 单 Agent：20 分钟完成，界面正常但核心功能损坏
- 多 Agent（分离生成和验收）：互相校验，能发现"看起来对但内部断了"的问题

### 验收三步法

1. **一个词描述结果**："能用"还是"损坏"？不是"感觉差不多"
2. **找到一个最具体的问题**：不是"整体感觉不对"，是"第二个按钮点下去没有反应"
3. **用用户的语言描述**：不是"第127行有bug"，是"我按了按钮什么都没发生"

> 生成和验收分离——这是可验证的工程规律，不是个人偏好。

## 任务级 vs 产品级

| | 任务级 | 产品级 |
|---|---|---|
| 特征 | 每次独立事件，没有积累 | 判断提前固化成字段结构 |
| 第100次 vs 第1次 | 一样费力 | 快3倍，结果更好 |
| 本质 | 平行的一百条对话 | 串联的迭代链 |
| AI 角色 | 每次重新"谈判" | 给 AI 下工单 |

> 产品级的本质，是把你脑子里的判断力外化成结构，让 AI 和其他人可以复用。

## 飞轮设计

### 成长规律

| 阶段 | 含义 |
|---|---|
| **一次成功 = 案例** | 不确定下次能不能复制 |
| **三次成功 = 方法** | 模式浮现，知道什么条件下能成功 |
| **十次成功 = 系统** | 变成可随时调用的 SOP，可以教给别人 |

### 飞轮的三个实体

1. **AI 业务档案**（越厚，每次对话起点越高）
2. **Prompt 模板库**（越多，启动成本越低）
3. **行业暗规则清单**（越多，AI 越少犯行业错误）

> 你的护城河不是技术，不是工具，是时间。是你比别人早了 N 圈这件事本身。

### 成果归集文档：「AI 第一圈 · [你的名字]」

每次做新产品就更新——加一个"第N圈"、加新提示词、更新业务档案。

## 两个真实案例

### 案例一：软件公司 30% → 3 倍

三层架构（工具没换，工作方式变了）：
1. **需求拆解层**：AI 把含糊需求分解成可执行功能单元
2. **代码执行层**：AI 生成代码，程序员从"写代码"变成"审查代码"
3. **审查验收层**：AI 辅助测试，人做最终判断

### 案例二：教育销售培训 PACED 框架

萃取销冠隐性判断的五维框架：
- **P（Pain）**：真实痛点 vs 家长嘴上说的
- **A（Authority）**：谁拍板？谁影响？
- **C（Capacity）**：看价格还是看价值？
- **E（Expectation）**：值不值的内在标准
- **D（Decision timeline）**：到决策点了吗？

设计：双轨存储（策略骨架 + 话术血肉分开）、双角色 AI 对练（家长 AI + 教练 AI 知识隔离）、策略判断权重最高的评分体系。

> [!summary] 可迁移性
> 凡是有"老手的隐性经验难以传给新人"这个痛点的行业，这套范式都能用。替换掉"教育销售"的行业知识，就能迁移到保险、医美、汽车、企业软件。

## AI 工具四级

| 级别 | 工具 | 模式 |
|---|---|---|
| 对话级 | 豆包、ChatGPT、Claude 对话端 | 你问它答 |
| 工程级 | Trae IDE 模式、Cursor | 你描述需求，AI 写代码，你验收 |
| 自主级 | Trae SOLO 模式 | 你只说要什么，AI 自己规划执行 |
| 系统级 | Claude Code | 命令行 AI 工程师，Hooks + Sub-agents |
